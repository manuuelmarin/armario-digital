# Auditoría del proyecto — 0.3.1

Fecha: 31 de octubre de 2026. Base revisada: `main`, PR #9, commit `7699ae52417b3be322f476ed22c1a9bde8ff238a`. Aplicación 0.3.0 al iniciar la revisión y 0.3.1 tras las correcciones. El esquema SQLite permanece en 9.

## Conclusión

Los cambios de la PR #9 estaban presentes en GitHub: se descargó `main` y sus 117 archivos coincidían con la copia local inicial. La suite anterior pasó sus 94 casos, pero no cubría seis problemas encontrados en la revisión del código y de los flujos. Se reprodujeron con doce casos nuevos que fallaban antes de corregirlos. Las correcciones y ampliaciones dejan 114 casos aprobados, incluidos siete recorridos reales de navegador.

La implementación sigue siendo local y opcional, conserva los flujos manuales y no introduce dependencias de ejecución. No se considera demostrada la calidad de los modelos ni su velocidad: las inferencias automatizadas son simuladas. Esta revisión no constituye una certificación de seguridad ni una garantía de ausencia de defectos.

## Hallazgos y correcciones

| ID | Área y efecto observado | Corrección aplicada | Evidencia |
|---|---|---|---|
| A01 | Sustituir una chaqueta o accesorio opcional podía producir un outfit sin esa pieza. Un vestido podía convertirse en superior + inferior | La sustitución exige la misma capa, excluye la pieza original y conserva el resto. Si no hay alternativa se informa; el formulario del outfit mantiene chaqueta y accesorios | Casos de chaqueta, accesorio y pieza única; recorrido sin JavaScript desde un outfit de cinco prendas |
| A02 | SQLite puede reutilizar el ID de una prenda eliminada. Otra prenda con los mismos atributos y revisión podía validar una captura anterior | Cada aprobación recibe `approval_id` único; la huella incluye su procedencia. Las capturas de recomendación usan versión 2 | Prenda borrada y recreada con el mismo ID, atributos e incluso fecha: se bloquea guardar la propuesta anterior |
| A03 | La huella guardada en SQLite no detectaba una modificación externa del archivo durante la inferencia ni antes de una aprobación manual | Se contrasta el archivo real al ejecutar/publicar resultados y al revisar/guardar; datos alterados o ausentes no se aceptan | Modificación durante visión, aprobación manual de foto alterada y eliminación previa a generación textual |
| A04 | Una base podía declarar esquema 9, carecer de tablas de IA y aun pasar la verificación mecánica de SQLite y de la copia | El contrato de tablas/columnas se deriva de las mismas migraciones. Arranque, creación, verificación y restauración comprueban la estructura y los ajustes obligatorios. El manifiesto exige enteros reales para formato y esquema | Tablas ausentes, columna eliminada, ajustes vacíos y formatos booleanos/nulos/decimales rechazados |
| A05 | Convertir un recorte transparente a JPEG podía colocar una prenda negra sobre fondo negro y hacerla invisible para visión | Composición sobre fondo claro antes de codificar el payload JPEG temporal | Imagen transparente con prenda negra: el fondo queda claro y la prenda conserva su oscuridad |
| A06 | Una tarea con versión antigua podía ejecutarse con instrucciones actuales conservando la atribución anterior | El trabajador marca esa tarea como caducada antes de invocar al modelo. El reintento crea una tarea con las versiones actuales | No se llama al modelo con versiones incompatibles; la regeneración explícita utiliza una captura vigente |

No se modifican los pesos, los prompts ni la elección de modelos por estas correcciones. No hay cambio de esquema de datos ni reconstrucción de tablas existentes.

## Evidencia ejecutada

Entorno: Linux, Python 3.12.14, Chromium 153 de una instalación temporal de QA. Las herramientas de auditoría se instalaron fuera del proyecto. CI conserva Windows y Linux con Python 3.12 y navegador en Linux; los resultados concretos de GitHub se consultan en la PR de esta revisión.

- Base anterior: **94 aprobadas**, incluidas seis de navegador.
- Tras corregir y ampliar: **114 aprobadas**, incluidas siete de navegador; **107 de servidor** cuando se omite navegador.
- Ruff, formato Python y formato Jinja aprobados.
- Revisión de escritorio a 1.440 px y móvil a 390 px; sustitución de una pieza sin JavaScript, controles conservados, imágenes y ausencia de desbordamiento horizontal.
- `run.py` ejecutado como proceso real con Waitress y carpeta temporal: respuesta 200, CSP y caché esperadas, Host ajeno rechazado con 400, origen de escritura ajeno con 403 y cierre comprobado. Esta comprobación se hizo aparte de pytest y de la cobertura.
- Análisis de **28 dependencias fijadas** de ejecución/desarrollo, incluida `colorama` de Windows: **0 vulnerabilidades conocidas** en la consulta de `pip-audit`. El [resultado JSON](dependencies-2026-10-31.json) conserva nombres y versiones. No equivale a ausencia de vulnerabilidades desconocidas.
- Cobertura instrumentada del paquete `armario`: **86 % combinando líneas y ramas**. El lanzador se prueba aparte, no se incluye en ese porcentaje. Cobertura no equivale a calidad ni prueba exhaustiva de fallos.

Comandos principales:

```bash
python -m ruff check .
python -m ruff format --check .
python -m djlint armario/templates --check
RUN_BROWSER_TESTS=1 python -m pytest -q
python -m coverage run --branch --source=armario -m pytest -q
python -m coverage report
```

Para la ejecución local de navegador se indicó `BROWSER_EXECUTABLE` al Chromium temporal. Para dependencias se analizaron las líneas fijadas de ambos requisitos, deduplicadas y sin marcadores de plataforma, con `pip-audit --no-deps --disable-pip --format json`; no se instalaron dependencias de aplicación nuevas ni se alteraron sus versiones.

## Actualización y compatibilidad

Se mantienen las tablas del esquema 9 y la versión 1 del perfil. `approval_id` se añade a la procedencia al guardar una revisión. Los perfiles anteriores siguen siendo legibles; las nuevas capturas incorporan su procedencia a la huella.

Las tareas de recomendación creadas con el formato anterior no deben guardarse como si se hubieran producido con las validaciones actuales. Se consideran caducadas y requieren **Reintentar con los datos actuales** o una nueva generación. Los outfits ya guardados y sus prendas no se eliminan. Las tareas con otra versión de instrucciones tampoco se ejecutan silenciosamente.

Las copias antiguas compatibles siguen verificándose según su propio esquema. Una copia con tablas/columnas ausentes no pasa por válida solo porque `PRAGMA integrity_check` devuelva `ok`; la restauración la rechaza antes de sustituir la carpeta activa.

## Validaciones que siguen necesitando otro entorno

No se han descargado ni ejecutado los pesos de Qwen. La exactitud de las siete descripciones, la calidad de combinación, memoria y latencia en un equipo de 32 GB requieren la prueba indicada en [IA local](../LOCAL_AI.md). La instalación interactiva de Windows/Ollama y macOS requieren comprobación manual en esas plataformas. La consulta real de meteorología y los fallos físicos de disco tampoco quedan demostrados por estos tests.

No se publica la app, no se configura Pages y no se crea un inventario personal para simular esas validaciones.
